## 2. 问题清单

### P0-1 线上后端没有内核模块

- 现象：`GET /api/kernel/tasks` 返回 404，前端「内核实验」进去必然报错。
- 原因：`KernelLabController` 只存在于 `feature/learning-loop-ui-rework`，`origin/main` 里没有；线上跑的是更早的 jar。
- 处理：用当前分支重新 `mvnw package` 出 jar 上传，或按第 7 节整体重发。

### P0-2 判分写死 Windows + WSL，服务器上不可能成功

- 位置：`KernelLabController` 三个常量 + `ProcessBuilder`。

```java
ST_ROOT = "G:\\ZhiCore\\kernel-lab"
STARTER = "/mnt/g/ZhiCore/kernel-lab/xv6-lab/xv6-riscv"
WORK    = "/mnt/g/ZhiCore/kernel-lab/web-run"
ProcessBuilder("wsl", "-d", "Ubuntu-24.04", "-u", "root", "bash", "-lc", script)
```

- 后果：Linux 服务器既没有 `wsl` 命令，也没有 `G:` 和 `/mnt/g`。线上即使更新 jar，提交也是 500。
- 这是「大问题」的核心：**当前实现只能在这台 Windows 开发机上跑**。

### P0-3 内核源码不在仓库里

- 现象：仓库中只有 `KernelLabController.java` 和两个 Vue 页面，没有任何 xv6 文件。
- 后果：别人拿到仓库无法复现判分，也没有「覆盖前」的基线源码。
- 处理：本次已入 `内核实验/xv6-riscv/`（第 8 节）。

### P0-4 v13/v14/v15 迁移脚本没进初始化序列

- 现象：`deploy/mysql-init/10-load-oslab-db.sh` 只加载到 v12，`docker-compose.yml` 也只挂载到 v12。
- 后果：全新环境里 `ai_session`、`ai_user_config`、`ai_help_event`、`ai_chunk_embedding`、`kernel_submission` 五张表都不存在。
  - AI 助手会话直接报错。
  - 内核提交会因为 `INSERT` 失败而被 `catch (Exception ignored)` 吞掉：页面显示「判完」，但历史记录为空，且不报错，极难排查。
- 处理：本次已补（第 8 节）。

### P1-1 `kernel_submission.id` 没有自增

- 建表：`id BIGINT NOT NULL PRIMARY KEY`，无 `AUTO_INCREMENT`。
- 代码用 `System.currentTimeMillis()*1000 + random(1000)` 手工造 id。
- 风险：并发同毫秒可能撞主键，撞了就被吞异常，记录静默丢失。表结构保持现状时，建议改成显式序列或加 `AUTO_INCREMENT`。

### P1-2 判分靠 grep 标记串，能用但很脆

- 只认单个 `marker` 字符串，输出里有这个词就 PASS，没有就 FAIL。
- 学生把 `printk("ZhiCore\n")` 写在 `if(0)` 里也能过。
- 上传内容含 `Makefile` 或 `../../` 会被直接拒（防越权覆盖），这是有意为之，别删。

### P1-3 每次提交全量复制 + 全量编译

- `cp -r` 整个 xv6 到 `web-run`，再 `make -j2` 全量编译，再起 QEMU 等 20 秒左右。
- 单次耗时数十秒到两分钟；两人同时提交就会互相抢 CPU 和磁盘。
- 一旦并发上来，需要排队或改成每次独立工作目录（`web-run/<userId>-<task>`）。

### P1-4 工作目录没有回收

- `web-upload/`、`web-run/`、`judge-run/` 都在仓库外，没有清理策略，长期跑会攒垃圾。

### P1-5 内核模块整体是「本机实验台」而不是「平台功能」

- 路径、工具链、判分方式都假设单机单用户。
- 要变成线上功能，必须做第 6 节的改造。改之前，这条路只能本机用。

### 3.4 内核判分额外要装（走「服务器自己判」这条路时）

```bash
sudo apt update
sudo apt install -y build-essential gcc-riscv64-linux-gnu qemu-system-misc
riscv64-linux-gnu-gcc --version   # 期望 13.x
qemu-system-riscv64 --version     # 期望 8.x
```

结论：`gcc-riscv64-linux-gnu` + `qemu-system-misc`（提供 `qemu-system-riscv64`）+ `make`，三样齐了就能编译 xv6 并跑起来。

### 3.5 目录与权限

```
/opt/oslab/                       # 部署根
/var/lib/oslab/kernel/starter/    # xv6 基线源码（只读）
/var/lib/oslab/kernel/work/       # 每次判分的临时工作目录（可写）
/var/lib/oslab/kernel/upload/     # 上传暂存
```

跑后端服务的用户（非 root）必须对 `work/`、`upload/` 有写权限。建议每次判分用独立子目录，判完删掉。

## 6. 要上线得改什么（建议，本次未改代码）

控制器里有三个写死的常量和一条 `wsl` 调用，改造点就这些：

1. 路径改成配置项，放 `application.yml`：

```yaml
oslab:
  kernel:
    enabled: true
    starter-dir: /var/lib/oslab/kernel/starter
    work-dir: /var/lib/oslab/kernel/work
    upload-dir: /var/lib/oslab/kernel/upload
    shell: ["/bin/bash", "-lc"]     # Windows 上配 ["wsl","-d","Ubuntu-24.04","-u","root","bash","-lc"]
    timeout-seconds: 180
```

2. `STARTER` / `WORK` / `upload` 从配置读，不再拼 `/mnt/g`。
3. `ProcessBuilder` 的第一个参数改成配置里的 shell 数组，Windows 与 Linux 各配一份。
4. `enabled: false` 时 `/kernel/*` 直接返回 503 + 明确文案，别让前端只看到 404/500。
5. 判分加串行队列（`Semaphore(1)` 或单线程池），避免并发把机器压死。
6. `work/` 用 `upload-<userId>-<task>-<ts>` 子目录，判完删除。

不做这几步，内核实验永远只能是「开发机上能跑」。

### 7.2 `kernel_submission` 结构

```sql
CREATE TABLE IF NOT EXISTS `kernel_submission` (
  `id` BIGINT NOT NULL PRIMARY KEY,          -- 无 AUTO_INCREMENT，代码手工造
  `userId` BIGINT NOT NULL,
  `task` VARCHAR(32) NOT NULL,               -- banner/cpus/memtop/pages/procs/nfile/ninode/hello
  `stage` VARCHAR(24) NOT NULL,              -- PASS / FAIL / BUILD_ERROR
  `passed` TINYINT NOT NULL DEFAULT 0,
  `seconds` DECIMAL(8,1) NOT NULL DEFAULT 0,
  `patchHash` VARCHAR(64) NULL,              -- 提交文本的 hashCode 十六进制
  `patchText` MEDIUMTEXT NULL,               -- 整份文件全文
  `logTail` TEXT NULL,                       -- 日志尾部 25 行
  `createTime` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY `idx_kernel_sub_user` (`userId`),
  KEY `idx_kernel_sub_task` (`task`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```
