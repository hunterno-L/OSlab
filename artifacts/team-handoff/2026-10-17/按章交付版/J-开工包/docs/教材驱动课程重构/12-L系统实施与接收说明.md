## 3. J/A 交付后 L 的操作顺序

1. 分别接收 J 的整章知识包、A 的整章题目包，核对 1.1—1.7 覆盖表、教材页码与待确认项。两包可先后到达，不接收逐节成果作为正式章节交付，也不合并旧 1.1 包。实验维护包另行接收。
2. 将原交付包归档。使用现有离线校验器检查格式和引用：在成员开工包根目录执行 `node tools/check-member-package.mjs .`。新节点建议由 L 确认并补入正式词表。
3. 登录 L 的管理员账号，进入课程内容管理。先核对来源登记和目录，再上传知识包及对应附件，预览后提交草稿。
4. 核对新节点与旧图谱的身份。已准备 [首章旧身份候选清单](13-第一章旧图谱身份核对清单.md)，覆盖 29 个预分配代码。完全同一知识点通过 nodeCode＋明确旧名称绑定；重名、拆分或实现节点另行决定。绑定应先于该新代码开始形成学生证据。
5. 查看图谱同步状态；有待同步项时处理错误并重试。不能把关系库导入成功直接当作图谱已经可用。
6. 上传 A 的题目包和图片。按 questionCode 核对新增／更新，版本冲突先处理。题目先为草稿，旧发布版在新修订发布前继续有效。
7. 独立接收实验维护包，先看 before/after、参考解和用例，依次提交、批准、明确应用。应用保留原 questionId，更新正式节点映射及单元草稿活动。运行核对后再启用对应课程资源，不因全部历史实验尚未维护完就阻塞第一章内容交付。
8. 审核并发布教材块和题目。启用实际用到且已验证的演示／实验资源。第一章不强制安排不适用的算法或实验。
9. 编排单元活动：讲解／情境例子 → 针对性练习 → 总结或检查点。引用原资源代码，不复制题目或实验。确认必需／可选与 SUBMIT／PASS 完成规则。
10. 依次提交、批准、发布单元。单元发布会检查引用和节点同步状态。
11. 使用学生账号完成整章学习，核对进度、作答反馈、个人证据、返回原活动和重新登录后的继续位置；整章验收后再推进下一章。

完整首章范围仍为 1.1—1.6 加本章复习，按十个预分配单元组织。材料缺口可保留在交接说明中；不要用页面置换样板填充首章。

一次正式交付可以在系统中分次上传、分单元检查；接口容量不决定成员交付粒度。修订反馈集中回到原整章包，沿用稳定代码，不恢复成逐小节打包流程。

## 4. 导入和修订规则

- 正式知识、题目、单元继续使用 `oslab-authoring/1.0`；实验维护使用 `oslab-experiment-maintenance/1.0`。成员无需调整现有模板。
- nodeCode、chunkCode、questionCode、unitCode、activityCode 承担稳定身份；显示名称可改，已有实验 ID 不换。
- 同代码无变化重导不增加实体或正文修订。提交再次执行服务端校验，不依赖浏览器上一次预览。
- 已发布内容保持原快照，修改只保存草稿；审核发布才切换学生可见版本。显式 revision 冲突会报错。
- 实验导入不会立即覆盖现行题目；APPLY 前保留旧版及新版快照，应用时核对现行内容未被另行修改。
- 题目图片随包上传。题面和选项图片随题目发布；解析图按本人作答解析记录开放。出处扫描件不因上传而直接开放。
- 学生提交与活动进度使用真实 attemptId／submissionId，并校验本人、资源和单元活动上下文。判题平台故障不记完成或失败。
- 旧标签仍可展示，但编程实验考查节点以 experiment_node 正式映射为准，不再按标签重复记证据。

详细接口见 [09 课程接口](09-已实现接口契约.md) 与 [11 身份测评实验接口](11-身份测评实验接口.md)。

在数据库脚本目录执行，替换为实际目标库和实际数据库认证配置：

```powershell

mysql --default-character-set=utf8mb4 --database=<目标库> --execute="source oslab_upgrade_v7_identity.sql"
```

本地工作库已执行增量迁移。此次最后补齐字段前后，学习事件 426、作答 246、掌握状态 13、原编程实验 64 条保持一致；这些是本地核对值，不是业务中写死的数量。未导入或发布 J/A 尚未交付的教材内容。
