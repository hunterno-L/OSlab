# L：教材驱动课程系统设计与改造执行计划

更新：2026-10-17。本文件可直接交给实施 agent。执行顺序按依赖组织，不安排开发日期。

本轮已交付设计、协作规范、样例及页面置换内容包；以下新增表、接口、页面和迁移步骤是待实施内容。当前内容发布优先完成第一章“计算机系统概述”整章。实施前以当前代码核对基线，保留已有有效功能和学生记录。

## 1. 目标与分工

把 OSLab 的学生主入口改为有目录、有连续内容、有明确下一步的课程学习。知识图谱和节点工作台承担查询、诊断与补救；题目、算法演示、实验继续关联知识节点，再由学习单元引用这些资源。

L 拥有课程结构、图谱词表、数据库、接口、单元编排、前端、校验、导入与发布。J 使用自己的教材整理内容、节点和关系；A 整理题目与答案、维护实验并填写新节点／学习单元映射。J、A 只提交完整资源包，不负责系统导入、数据库操作或在线联调。

首个交付目标：第一章“计算机系统概述”整章可学。学生从 1.1 开始，沿教材目录完成内容、例子、题目与本章复习，看到个人掌握证据并继续第二章。概念单元不要求强行安排算法模拟或编程实验；A 将适用实验作为实践或后续拓展关联。LRU 保留为后续算法闭环的技术样板，详见 [第一章方案](06-第一章交付方案与资料清单.md)。

必须保留两个产品能力：一是基于个人真实事件的数字孪生学习画像，包括概念／实践掌握、证据、历史变化与补救路径；二是题目练习、算法模拟、编程实验三个可直接访问的独立入口。课程单元复用现有资源与判分服务。

前端路径相对于 `前端代码/osLab-frontend/`，Java 路径相对于 `后端代码/osLab-backend/src/main/java/com/yupi/springbootinit/`。数据表以实际升级 SQL 为准，当前 MyBatis 关闭下划线自动转驼峰，新增列保持项目现有 camelCase 约定。

已有学习表基线位于 `数据库文件/oslab_upgrade_v3_learning.sql`，后续升级脚本继续单独增量维护。新表的 id 使用现有雪花 BIGINT，代码列采用 VARCHAR(128)，正文采用 TEXT／LONGTEXT，结构字段采用现有 JSON 序列化约定；统一保留 createTime、updateTime、isDelete。目录父项、单元顺序、活动顺序和用户继续位置分别建立查询索引，不用一份大 JSON 保存整门课程。

当前题目导入接口是 `POST /api/learning/questions/import/preview` 和 `/import/commit`，请求形状为 `{ "content": "JSON数组文本" }`，单次上限 100。现有提交审核逻辑要求作者提交，管理员审核发布。新版工具复用这条作者—审核人流程，明确展示每一步状态。

现有创建、管理、导入接口要求 admin，尚无独立内容编辑角色。当前由 L 使用自己的真实账号执行导入与发布，材料 contributor 单独保留 J／A 的整理身份；不需要为成员配置管理账号。学生端验收由 L 使用测试学生账号执行。

当前图谱 `/api/knowledge_graph/addNode`、`/addRelation` 只支持旧字段和逐项写入。不要把它们描述为已经支持新版知识包。新版接口沿用现有登录和管理权限即可，暂不扩大角色系统。

## 3. 数据模型：确定的设计

### 3.1 目录、节点与内容

| 表 | 核心列 | 约束与用途 |
| --- | --- | --- |
| `course` | id, courseCode, title, description, sourceCode, status | courseCode 唯一；一门课程的目录与发布入口 |
| `course_section` | id, sectionCode, courseId, parentId, title, textbookNumber, sortOrder, sectionType, extension | sectionCode 唯一；树形目录，不用节点关系代替目录 |
| `textbook_source` | id, sourceCode, title, edition, editionConfirmed, sourceType, metadataJson | sourceCode 唯一；版本、定位说明和素材根目录 |
| `knowledge_node_registry` | id, nodeCode, name, nodeType, description, aliasesJson, homeSectionId, sourceRefsJson, status, revision, graphSyncStatus | nodeCode 唯一；知识身份和编辑属性的主记录 |
| `knowledge_node_legacy_map` | id, legacyGraphId, legacyName, nodeCode, resolutionNote | 导入前导出旧节点，保存明确映射；同名存在歧义时不按名字自动合并 |
| `knowledge_relation` | id, fromNodeCode, toNodeCode, relationType, reason, sourceRefJson, status | 三列组合唯一；保留依据和审核状态，投影到 Neo4j |
| `learning_content_chunk` | id, chunkCode, sectionId, chunkType, title, contentMd, sourceRefJson, assetsJson, status, revision | chunkCode 唯一；教学块保存完整语义 |
| `learning_chunk_node` | chunkId, nodeCode | 联合唯一；一个块解释多个节点 |

MySQL 登记表维护稳定身份、内容和审核依据；Neo4j 继续承载知识关系查询与图谱显示。所有图谱写操作经过同一应用服务：登记草稿 → 同步图谱 → 标记同步结果。失败后按代码重新同步，不新增另一份实体；成功后才可发布对应内容。不引入消息中间件或分布式事务。

Neo4j `Entity` 增加 `nodeCode` 唯一约束，显示名不设全局唯一。新关系用规范代码存储。旧 `dependent/contain/related/implements` 对应 `REQUIRES/CONTAINS/RELATED_TO/IMPLEMENTS`，兼容历史 `implemente`。`REQUIRES` 保持“后学节点 → 前置节点”的方向；路径展示反向排列即可。

新增 `CONTRASTS_WITH`、`BASED_ON`；无方向的对比和相关关系按两端代码排序存一条。前置路径只使用 `REQUIRES`，不把包含关系和一般关联当作前置。

### 3.2 学习单元与资源

| 表 | 核心列 | 约束与用途 |
| --- | --- | --- |
| `learning_unit` | id, unitCode, courseId, sectionId, title, objectivesJson, sortOrder, status, estimatedMinutes, revision | unitCode 唯一；一个明确学习目标及其流程 |
| `learning_unit_node` | unitId, nodeCode, role | 联合唯一；TEACHES / PREREQUISITE / EXTENSION |
| `learning_resource` | id, resourceCode, title, resourceType, algorithmKey, adapterKey, sourceRefJson, resourceConfigJson, status | resourceCode 唯一；登记 DEMO、EXPERIMENT、DOCUMENT 等资源 |
| `learning_resource_node` | resourceId, nodeCode, role | 联合唯一；资源关联知识 |
| `learning_unit_activity` | id, activityCode, unitId, activityType, title, sortOrder, referenceType, referenceCode, configJson, required, completionRule | activityCode 唯一；按代码引用块、题目或资源，单元内有固定顺序 |
| `learning_unit_progress` | userId, unitId, unitRevision, currentActivityCode, completedCount, requiredCount, progressStatus, goalStatus, updatedTime | 用户—单元唯一；进度与达标状态分列 |
| `learning_activity_progress` | userId, activityId, state, resultSummaryJson, attemptId, eventGroupKey, updatedTime | 用户—活动唯一；可追溯一次真实作答或演示完成 |

引用类型使用 `CHUNK/QUESTION/RESOURCE`。`READING/WORKED_EXAMPLE/SUMMARY` 引用内容块，`PRACTICE/ASSESSMENT` 引用题目，`DEMO/EXPERIMENT` 引用资源。首期每个题目活动只引用一道题；需要题组时由多个活动或现有测评队列组合，避免再造题目副本。

课程目录可以显示某节下多个单元；只有一个单元时直接点击进入，不增加没有意义的中间页。章节进度根据本章已发布必需活动聚合，不能继续用“有证据节点比例”代替课程学习进度。

### 3.3 题目、实验与历史记录

在现有 `learning_question` 增加 `questionCode` 唯一列、sectionId、sourceRefJson、parentQuestionCode、partIndex、revision；稳定代码导入更新原 ID。题目选项、答案、解析沿用当前字段，不新建第二套题库。

`learning_question_node` 增加 nodeCode、role，保留 weight，逐步替代 nodeName 关联。默认主节点 1.0，次节点 0.3。权重是观测影响系数，不是评分比例；实现时让 BKT 服务真正接收映射权重，不能只是把字段保存下来。以一次作答 eventGroupKey 将多个节点观测归为同一事件组。

现有 `LearningEventServiceImpl` 已将映射权重用于综合 pKnown：`after = before + weight × (完整BKT更新 - before)`，概念／实践分项仍采用当前冻结更新规则。新版导入要传入已有权重通路，首期保留这个模型语义；历史迁移不同时改动 BKT 公式。事件快照应保留当次权重与模型版本，便于解释未来数据。

新建 `experiment_node`：questionId、nodeCode、role、weight，组合唯一。现有代码题 `question`、`question_submit` 和判题流程继续使用；给实验登记 `resourceCode` 并保留原 questionId。A 提交实验修订与映射文件，L 通过工具应用到原记录；旧标签仅生成候选，缺少节点由 J 补充后再绑定。

`experiment_node` 是编程实验考查节点、角色与权重的唯一编辑来源；通用资源节点展示从它读取，不让 A 在两处重复维护。实验到单元的编排使用 `learning_unit_activity` 的 EXPERIMENT 活动；A 填写适用单元、必需／可选、完成条件和理由，管理工具保存为单元活动草稿，由L确认顺序并发布。已有同一引用的活动保持 activityCode，不重复插入。

把 `LearningResourceResolver.findExperimentsByNode`、判题终态事件、节点工作台、导师与教师覆盖统计统一改为读取正式实验映射。尤其 `recordJudgeEvents` 当前仍解析 tags 并按固定 1.0 更新；新实现需读取 nodeCode、role、weight，使用同一实验映射服务。图谱改名后仍能定位实验，不能只修显示列表而让判题更新走旧标签。

`learning_attempt` 增加 questionRevision、answerSnapshotJson、sourceUnitCode、sourceActivityCode；`learning_event` 增加 nodeCode、sourceUnitCode、sourceActivityCode。编程实验提交同样保存可选的单元／活动上下文，判题终态据此完成对应活动。新作答保存当时的判分依据与上下文，单元页面提交仍调用同一判分服务。

历史事件的判分结果、快照、事件组和已用幂等键不重算、不改成新规则。可以补充 nodeCode 定位列，但保留当时的节点名称。题目修订不清空历史首次作答资格，也不通过新建重复题目获得另一份首次证据。

`learning_question_revision` 保存 questionId、revision、contentSnapshotJson、reviewStatus、authorId、reviewerId 和发布时间。已发布题目的重导如无变化则不写新版本；有变化时创建草稿修订，当前发布题面继续有效。修订审核发布后更新题目的有效版本及当前字段，题目 ID 保持不变。当前审核服务需扩展为审核这一修订，再激活新版本，不能直接覆盖已发布题面。

现有记录只有冻结结果而无完整题面快照的，明确按历史冻结结果显示；不能倒推或捏造旧题面。内容块采用相同的草稿修订与发布逻辑，单元中正在阅读的内容带 revision，刷新后明确采用当前已发布版本。

目录与单元重排不抹除已完成活动：activityCode 未变时继承进度，新增必需活动时提示补充，移除活动不把课程统计变成负数。

进度枚举使用 NOT_STARTED / IN_PROGRESS / COMPLETED；单元 goalStatus 使用 NOT_CHECKED / PASSED / REVIEW_RECOMMENDED。完成必需流程可以进入 COMPLETED，但检查点失败时 goalStatus 仍为 REVIEW_RECOMMENDED。optional 活动不进入必需活动分母。

## 4. 接口与路由：新增清单

以下为拟新增接口，以项目现有 BaseResponse、校验和权限约定实现。GET 参数使用代码，写入接口带课程／单元与活动上下文。

| 接口 | 职责 |
| --- | --- |
| `GET /api/courses` | 学生可见课程、学习进度、继续入口 |
| `GET /api/courses/{courseCode}/outline` | 目录树、已发布单元及当前用户进度 |
| `GET /api/courses/{courseCode}/resume` | 首个单元或最后学习位置，返回明确理由 |
| `GET /api/courses/units/{unitCode}` | 目标、资源顺序、当前活动、前后单元与相关节点 |
| `POST /api/courses/activities/{activityCode}/complete` | 阅读确认、演示终步等进度更新；不能直接写掌握度或上传正确标志 |
| `GET /api/courses/nodes/{nodeCode}/units` | 节点在哪些单元中教授／作为前置 |
| `POST /api/teaching/content/import/preview` | 校验新版知识包，解析出处和素材，返回新增／更新清单 |
| `POST /api/teaching/content/import/commit` | 导入知识草稿，按稳定代码更新，同步 Neo4j，返回逐项结果 |
| `POST /api/teaching/assessments/import/preview` | 校验新版题目包、答案、编号、节点和来源 |
| `POST /api/teaching/assessments/import/commit` | 保留原题 ID 的新增／更新，写入来源与权重 |
| `GET/PUT /api/teaching/experiments/{questionId}/mappings` | 拟新增：L 应用 A 提交的实验节点和单元映射；生成或更新单元活动草稿 |
| `GET/PUT /api/teaching/courses/{courseCode}/outline` | 目录维护与顺序调整 |
| `GET/PUT /api/teaching/units/{unitCode}` | 单元目标、节点、活动及完成规则编排 |
| `POST /api/teaching/units/{unitCode}/publish` | 检查引用资源状态后发布，返回阻碍发布的具体条目 |

新增学生页面 `/courses`、`/courses/:courseCode`、`/courses/:courseCode/units/:unitCode`。知识工作台增加按代码入口，例如 `/knowledge/concept/:nodeCode`；旧 `/knowledge/node/:nodeName` 用显式历史映射解析并跳转，重名时返回候选而不是随机选择。

现有 `/assessments`、`/experiments/simulation`、`/experiments` 和 `/experiments/code/:id` 保留，不重定向到课程页。首页和导航提供“题目练习／算法模拟／编程实验”直达入口；统一导航配置控制选中态。资源支持无单元上下文直接使用；从单元进入时附带返回位置，并在活动结果中保存真实上下文。

旧题目导入接口保留用于已有工具，不悄悄改变请求形状。新代码接口返回 nodeCode 和 name，迁移期同时接受旧参数，并由共享解析器转换，不在每个服务里各写一套名称匹配。

单元学生接口只下发已发布内容。活动引用题目时复用现有学生题目 VO，标准答案继续留在后端，解析沿用本人作答后下发规则；不能因为把题目嵌入单元，就直接下发完整管理题目对象。

## 5. 导入与审核的实际流程

知识包和题目包使用 [协作数据规范](05-协作数据规范.md) 与仓库样例。导入预览列出：新增、更新、未改动、错误、需要确认的映射；错误定位到数组项与字段。

提交执行同一套服务器校验，不把客户端预览结果当作事实。按 nodeCode、chunkCode、questionCode 更新；一个批次保留 importRunCode、操作者和数量，支持再次提交原包而不增加重复实体。带 revision 的已修改条目出现版本冲突时，展示差异，由L选择覆盖或合并。

知识资源和题目先导入为 DRAFT，沿用现有审核状态。系统作者／导入操作者使用 L 的真实账号；材料来源 contributor 保留 J 或 A，不将其冒充成登录用户。由 L 完成提交审核和发布，无需 J、A 进入系统；现有审核接口涉及 authorId 时使用实际导入身份。

目录与正式节点编号由L批准；J 可以在知识包中提出新节点和候选关系。单元发布时，讲解块、题目、资源必须存在且可用；草稿单元可以引用已登记但尚未完成的素材，便于提前编排。

### 阶段 1：稳定身份和旧数据迁移

任务：

1. 添加 nodeCode、questionCode 等列和登记表，先允许旧数据尚未映射。
2. 将旧节点逐项登记；普通改名沿用代码，拆合节点写单独决议。旧题目分配保留原 ID 的 `q.legacy.<id>`，实际教材题经人工确认后绑定正式来源代码。
3. 回填题目、内容、事件、掌握度及资源关联的节点代码；处理全部名称歧义后，再对新业务写入启用必填和唯一约束。
4. 将掌握度唯一定位从 userId+nodeName 迁移到 userId+nodeCode。遇到同一代码的多条旧汇总时，根据真实事件重放现有算法或确定一条有效记录，不能相加概率和计数后称作迁移成功。
5. 修改图谱、工作台、题目、导师、推荐、教师统计和缓存的查询键。保留历史名称供旧链接和证据显示。

主要参考：`useNodeWorkbench.ts`、`LearningPathServiceImpl.java`、`LearningTeacherServiceImpl.java`、`LearningResourceResolver.java`、现有事件幂等逻辑。

验证：重命名 LRU 后相关题目、事件和单元引用仍一致；CPU FCFS 与磁盘 FCFS 不混淆；迁移前后的用户历史事件数量、冻结判分结果和可回放结果相同。

### 阶段 2：目录、来源、内容块和新版导入

任务：

1. 建立五章目录；正文、小结、练习、答案分别登记，不把它们全部变成知识实体。
2. 实现知识包和题目包的预览／提交，接收新版完整字段，输出代码—数据库 ID 对照。
3. 统一答案校验：JUDGE 字符串 true/false；SINGLE 一个现有选项；MULTIPLE 无重复的选项集合；FILL_BLANK 为单空可接受写法。
4. 新版导入要求解析和主考查节点完整；图片保留相对路径，在资源发布时转为可访问地址，Markdown 渲染复用项目组件。
5. 管理端增加知识导入、词表、来源查看和审核；A 的界面展示稳定题号、版本和节点权重。
6. 题卡目前用普通文本插值显示题干、选项和解析，不能直接呈现教材 Markdown 表格与图片。复用 `src/components/MdViewer.vue` 替换这些展示，补齐统一数学公式渲染；现有 Viewer 只有 GFM 和代码高亮插件，公式支持尚待实现。

主要参考：`model/dto/learning/LearningQuestionAddRequest.java`、`learning/LearningQuestionGrader.java`、`src/views/learning/ManageLearningQuestionsView.vue`、`src/api/learning.ts`、`src/components/learning/QuestionAnswerCard.vue`。

验证：同包导入两次只更新原 ID；未知节点代码能定位；四种题型均能判分；单空别名匹配与多选集合匹配一致；截图来源可定位；J 的块能在节点抽屉预览。

### 阶段 3：课程与学习单元页面

任务：

1. 实现课程目录、单元编排和用户进度接口，按第一章方案导入实际内容与单元。页面置换七单元草案保留作后续联调；不同时导入 samples 中同代码的旧样例单元。
2. 学生登录后进入课程页。首访显示开始学习；已有位置显示继续学习，带目标和剩余活动。
3. 单元页采用左侧目录、中部内容、相关知识抽屉；延续现有浅色、细边框、蓝色强调。阅读栏保持可读行宽，不把旧节点工作台原样塞进主区域。
4. 阅读与例子明确确认完成；题目提交和模拟完成从真实服务结果更新进度。页面刷新恢复当前位置，离开单元后再进入仍可继续。
5. 点击知识词打开现有抽屉；关闭回到原活动与滚动位置。节点页增加“在课程中学习”的单元入口。
6. 原图谱、自由题库、实验中心继续保留。不要让学生第一次进入必须分析完整图谱。
7. 首页提供题目练习、算法模拟、编程实验三个直达入口；与课程入口共用实际资源数据。独立入口无需 unitCode 也能运行、作答和提交。

主要参考：`HomeView.vue`、`src/navigation/appNavigation.ts`、`src/router/routes.ts`、`NodeWorkbenchDrawer.vue`、`NodeLearningWorkspaceView.vue`、现有共用布局。

验证：新生、已完成部分活动的学生、完成单元的学生三种状态都有明确下一步；窄屏目录可折叠；管理员仍能进入教学管理。L手动审核界面，不使用浏览器自动化代替其审美判断。

### 阶段 4：演示与实验纳入单元活动

任务：

1. 建立资源登记表，从 [演示清单](../../content/operating-systems/wangdao-2025/catalog/demos.json) 对齐教材与知识节点。
2. 先复用 OSLab 现有页面置换与 CPU 模拟。现有代码题登记实验资源，并建立确认过的 experiment_node 映射。
3. 旧 Vue 2 项目逐个抽取算法、案例和可视化逻辑，嵌入 Vue 3 的统一活动外壳，不重建重复菜单。`Replacement_FF.vue` 实际为 FIFO，不能误登记成内存首次适应。
4. 后续算法扩展再补 HRRN、优先级、MLFQ、分区分配和磁盘调度；每个算法有输入、步骤、运行控制、解释、结果和重置。第一章交付只要求已有独立模拟入口可用，不以全部 18 个演示适配完成为前提。
5. 若先临时嵌入旧项目，使用独立资源路径、hash 路由和正确 publicPath，移除旧全局导航；与宿主页通过明确活动标识报告终步。此报告只计进度，挑战判分必须走现有后端或新算法服务。
6. 长期以原生适配器为目标。`adapterKey` 选择实现，`algorithmKey` 标识算法，同一 demo 可由不同单元传入不同参数。
7. 按 [A 的实验指南](07-成员A编程实验维护与映射指南.md) 接收实验维护包。A 以原 ID 提交题面、参考解、用例及两类映射，L 核对当前库并保存修订、映射与活动草稿。没有第一章适用实验时保留后续归属。

主要参考：现有 `SimulationView.vue`、`LearningSimulationServiceImpl.java`、旧演示项目 `src/router/index.js` 与 `src/views/unit3/`、`unit4/`、`unit5/`。

验证：FIFO/LRU/OPT 标准序列、RR 到达时刻、优先级抢占、SCAN 边界／方向等测试有确定结果；暂停、单步、重置有效；观看演示不提高掌握度，真实挑战结果才写证据；从编程实验返回原单元与活动。

实验映射验证：保留 questionId 与历史提交；节点列表、导师、教师覆盖和判题事件均读取相同正式映射；修改显示名称后关联不丢失；一次判题不同时按新映射和旧 tags 重复计证据。

### 阶段 5：进度、诊断与补救闭环

任务：

1. 一次题目提交只判分一次、形成一个真实事件组；活动进度引用该结果，不重复调用判分形成额外事件。
2. 按题目和实验明确映射更新节点掌握；不把当前单元所有节点、前置或同章知识都标成已掌握或薄弱。
3. 前置薄弱时推荐它所属的已发布单元／活动。记录原学习位置，完成补充后返回主线。
4. 节点工作台与单元详情都展示证据来源、日期、考查节点和补充建议。课程完成比例与知识掌握图分开展示。
5. 图谱查询可按教材目录和知识层级过滤；增加规范关系的筛选和解释，默认只展示当前学习附近的关系。
6. 导师检索从完整教学块生成带 parentChunkCode 的片段，返回来源章节和页码。先完成可查证的教材内容问答，再扩展复杂 GraphRAG；正文不由 AI 临时生成后假称教材。
7. 保留数字孪生的个人图谱、双维掌握、证据列表、历史快照及推荐。概述章没有实践观测的节点显示“未评估”，不能用概念作答填充实践分，也不因为读完章节给全部节点上色。
8. 独立题库、模拟和实验的有效结果照常更新同一画像；单元进度只完成当前提交明确关联的活动。重复题目与旧历史继续复用已有事件规则。

主要参考：`LearningEventServiceImpl.java`、`LearningMasteryServiceImpl.java`、`LearningPathServiceImpl.java`、导师服务、学习记录和图谱页面。

验证：读完单元但答错检查点时，流程可以完成，达标情况仍显示建议复习；同题从不同入口作答不获得额外首次证据；复习不破坏原继续位置；导师出处指向真实教学块。

2. J、A 交付整理好的知识、题目及实验维护包；L 校验、导入、保存映射、确认编排并发布。第一章以适合本章的活动组合验收，四类题型不要求每节凑齐。
3. 检查后端构建、前端构建、已有学习验证脚本与新增必要测试。更新 README、字段说明和交付文档，明确已发布范围与草稿范围。
4. 按此样板分章扩展素材和单元，现有授权演示逐个验收后启用。部署按L实际安排执行，不把本地验收当作线上已更新。

验收路径：登录新学生 → 第一章 1.1 → 阅读／情境例子 → 知识测评 → 解析／补救 → 节点画像 → 返回单元 → 后续小节 → 本章复习 → 重新登录继续。同时从独立入口分别进入题目练习、算法模拟、编程实验，验证原功能仍可使用。LRU 的演示／实验闭环作为后续专项验收。

## 7. 必须有的验证与交付物

只为真实风险添加测试：稳定编号迁移、重复导入、四类判分、权重观测、前置方向、单元进度和历史结果一致性。外观由L按实际页面人工检查，常规样式修改不增加镜像实现的单元测试。

最终提交给L：

- 数据迁移脚本与旧 ID／名称—新代码映射报告。
- 知识包、题目包、素材与导入结果。
- 可编辑的第一章目录、教学单元与本章复习，以及内容、测评、画像和继续位置的完整交付；页面置换七单元保留为后续草案。
- A 的编程实验维护清单、旧 ID—资源代码对应、实验—新节点／学习单元映射与运行核对结果。
- 三个独立资源入口验证，以及课程内外共用个人画像与事件的验证记录。
- 18 个演示的登记状态和已运行验证清单。
- 学生闭环验证结果，已发布内容范围与后续待补清单。

L无需等待五章全部整理后才验证产品。第一单元可用之后，J、A 按同一协议持续增加内容，系统不再为每个新节点开发一个静态页面。
