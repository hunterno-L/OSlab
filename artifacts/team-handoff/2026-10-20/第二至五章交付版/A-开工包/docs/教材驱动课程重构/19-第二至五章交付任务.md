# 第二至五章：J／A 连续按章交付任务

更新：2026-10-20。参考《2025 王道操作系统》。本任务说明适用于第二章起的连续交付；第一章材料保持现有成果，不因任务升级重做。与旧文档中的“只整理第一章”“综合题仅列候选”“单元全部由 L 编排”冲突时，以本文为准。

## 1. 顺序与范围

J、A 从第二章开始一直整理到第五章，**一章一章交付，交完即可继续下一章，不必等待 L 导入上一章**。每章内部可按节制作，不拆成零散小节正式交包，也不等四章全部完成才一次性交付。

| 章 | 教材范围 | 章代码／批次词根 | 主要内容 |
| --- | --- | --- | --- |
| 第二章 进程与线程 | 2.1—2.5 | `sec.process`／`process` | 进程线程、CPU 调度、同步互斥、死锁、疑难点 |
| 第三章 内存管理 | 3.1—3.3 | `sec.memory`／`memory` | 内存管理、虚拟内存、疑难点 |
| 第四章 文件管理 | 4.1—4.4 | `sec.files`／`files` | 文件基础、目录、文件系统、疑难点 |

书上实际正文、例题、图表、习题和答案为范围依据。目录已有代码复用；缺少小标题由 J 在章节方案中补齐。章末疑难点纳入复习，不把“习题精选／答案解析”建为知识实体。

## 2. 分工调整：内容整理尽量在成员侧完成

| 工作 | J | A | L |
| --- | --- | --- | --- |

| 题目 | 提供术语与易混点 | 覆盖教材选择题及综合应用题，补合适的判断／填空／多选 | 维护系统题型与评分能力 |

J/A 直接交换资源文件，无需由 L 手工中转。准确、无冲突的新增代码可先在两人的文件中共同使用，标为候选；L 最后一次性确认，不要求每新增一个节点就停工等待批准。已存在代码不随意改义、换号或重复新建。

不把“缺内容、缺框架、没整理答案”统一留成 L 待办。确定的内容问题在交包前修好；真正缺教学内核源码或特殊执行条件时，A 交付已完成文件，并给出具体依赖、建议方案和可复现步骤。

## 3. J 每章交付

```text
J-第二章-知识-001/
├─ knowledge.json
├─ chapter-plan.json
├─ assets/
├─ 交接说明.md
└─ 自审记录.md
```

后续替换为第三／四／五章；`batchCode` 分别为 `batch.j.process.chapter.001`、`batch.j.memory.chapter.001`、`batch.j.files.chapter.001`、`batch.j.io.chapter.001`。修订实体沿用 nodeCode／chunkCode；版本号写交接说明。

`knowledge.json` 沿用现有 `oslab-authoring/1.0`，完成本章节点、语义完整教学块、关系和出处；复用前章节点时保持含义。不要为控制图谱复杂度删掉有明确教学价值的主干关系，关系密度与初学界面是否全量展开是不同问题。

`chapter-plan.json` 是给 L 的**编排建议文件**，当前不是直接导入接口。形状见开工包空模板及 `reference/samples/chapter-plan.sample.json`：

- `schemaVersion=oslab-chapter-plan/1.0`，`chapterCode` 填章代码，`status=PROPOSED`。
- `sections` 只列目录表中缺失或需要调整的小标题：sectionCode、parentSectionCode、title、textbookNumber、sortOrder、sectionType、pageStart、extension。页码实际核对，不从示例复制。
- `units` 列 unitCode、sectionCode、title、objectives、sortOrder、estimatedMinutes、prerequisiteUnitCodes、nodeCodes、readingChunkCodes、demoResourceCodes、practiceGuidance。
- `readingChunkCodes` 就是建议阅读顺序；每个教学块至少被一个单元引用，补充块在 practiceGuidance 注明选读。单元目标是学生可完成的任务，不把每个段落机械设为一个单元。
- 演示只引用 shared/demos.json 中的真实资源代码；说明适合观察或预测的任务。未接入的资源可以建议，不写已运行通过。

单元建议通常按“概念／机制 → 完整例子 → 自测 → 实践或总结”组织。复杂的同步、死锁、地址转换可以拆多个单元；简单小节可以合并，数量由教学连贯性决定。知识关系可以跨章，先修节点与先修单元分开说明。

J 的交接说明附逐节覆盖表、节点增改清单、核心易混点；自审检查块是否可顺读、主干关系是否合理、所有图片是否可读。J 先把本章可用的 knowledge.json 和 chapter-plan.json 发给 A 作对照，不必等 L 导入。

## 4. A 每章交付题目包

```text
A-第二章-题目-001/
├─ questions.json
├─ application-questions.json
├─ assets/
├─ 交接说明.md
└─ 自审记录.md
```

`questions.json` 保留当前四种客观题协议；`application-questions.json` 收录综合应用、计算推演、简答证明、算法设计及作图任务，规范见 [综合应用题资源规范](20-综合应用题资源规范.md)。两者属于**同一章题目交付包**，不另外拆一次交付。

对应批次：`batch.a.process.chapter.001`、`batch.a.memory.chapter.001`、`batch.a.files.chapter.001`、`batch.a.io.chapter.001`。应用题批次可在相同词根后加 `.application`。

收录以教材实际习题为基础，**不能因系统暂不支持主观评分而跳过综合应用题**。保留题目材料、各小问、参考答案、关键过程、评分点和考查映射；不把大题全拆成选择题以凑支持范围。教材只有选择题的部分不强制变题型，但可围绕关键概念适量补判断、单空填空、多选，标清 SELF_AUTHORED。题型覆盖以实际学习需要和教材为准，不设题数比例。

每章给出“教材位置／题型组／原题号 → questionCode”收录表，分别统计客观题与应用题，漏题注明真实原因。选择题与综合题各自从 01 编号时，应用题用 `q.wd25.s2_4.app.001` 一类代码，防止撞号。已交题号保持不变。

题目出处与答案出处都要可定位；综合题提供同题的评分细则，按小问标记真正考查的节点。多解题给出可接受方法，不能只给最终数字。应用题的参考资料与评分点先供 L 接入自评／教师评阅；平台当前不支持自动主观评分。

## 5. A 每章的实验维护包

实验维护继续独立于题目包：`A-第二章-实验维护-001`，之后按章替换。使用 `batch.a.experiments.process.001` 等批次；同一实验跨章使用只在主归属章节维护一次，其他章引用原 resourceCode。

先读原实验快照，优先处理**编辑区没有初始代码、题面无有效任务、参考解缺失、测试为占位**的条目。原 `questionId` 不变。每个声称已修订的实验必须交实际修改文件，不能再次仅交 contentChanges=[] 和盘点说明。

每项交付至少包含：

1. 学生需要完成的任务、输入输出／数据范围、函数接口或环境约定。
2. 可直接放入编辑区的 `starter.c` 等初始代码：保留 include、数据结构、main／调用入口、必要上下文和 TODO；不把完整参考答案当框架。优先维护原实验已有语言，不为每题硬做四种语言。
3. 独立 `reference.c` 等完整参考实现与解题说明，作为管理资料。
4. `judge-cases.json` 的真实输入输出，覆盖正常、边界及常见错误；不保留无意义 123→123 占位。
5. 本地编译／运行命令、环境、预期／实际结果，以及至少一个典型错误实现会被哪条用例识别。
6. 新知识节点和单元映射；缺号时与 J 对齐后补齐，确实待定的给出具体建议。

编辑框对应数据库字段是 `originalCode`，维护包通过 `{field:"originalCode",file:"experiment-files/原ID/starter.c",reason:"补齐学生起始框架"}` 提交；不是 `initialCode`，也不是语言映射 JSON。其余允许字段为 content、answer、judgeCase、judgeConfig、tags。完整字段规范见实验指南。

**完整教学内核任务**：A 先整理需要的上下文代码、函数契约、构建命令、预期行为和可取得的工程资源；无法仅靠单文件运行时给出具体工程适配包／说明，L 负责平台执行适配。不要把原内核实验偷偷改成打印固定答案的小程序，也不要因缺平台环境而放弃能完成的框架和参考实现工作。

验收分为“文件已修订”“本地运行已验证”“平台待联调”，分别记录。已有本地工具链时 A 完成本地运行；确有环境缺失时注明缺项。L 验收新框架还要检查浏览器中旧的空草稿是否覆盖 originalCode，这属于系统侧工作。

## 6. 离线核对与交包

新版开工包为每章提供单独工作目录 `work/ch02` 至 `work/ch05`，A 另有 `experiment-work/ch02` 至 `ch05`。以第二章为例：

```powershell
# J：本章知识与编排建议
node tools/check-member-package.mjs . --work-dir work/ch02

# A：直接引用 J 发来的本章交付目录，对齐候选节点和单元
node tools/check-member-package.mjs . --work-dir work/ch02 --with-j "../J-第二章-知识-001"

# A：本章实际实验修订
node tools/check-member-package.mjs . --work-dir experiment-work/ch02 --with-j "../J-第二章-知识-001"
```

这些命令只查文件；候选目录／单元和综合题通过检查不代表平台已经接入。最终交付只打包本章工作目录里的实际成果，不把四章空模板、shared/ 和原全量实验快照一起回交。没有本章实验维护时说明无适用项，不交空包冒充完成。

引用前面已交章节的新节点或先修单元时，`--with-j` 可重复：例如 J 检查第三章加 `--with-j work/ch02`；A 检查第三章可以同时加 `--with-j "../J-第二章-知识-001" --with-j "../J-第三章-知识-001"`。参数只读文件，不要求 L 先导入这些候选编号。

每章交接说明控制在实际覆盖、变更、验证及少量待定项；J/A 自行修好确定问题，不用写冗长的免责说明。L 不再逐项补录答案、重写框架或替成员补主考映射。

## 7. L 保留的系统工作

L 继续负责：候选代码最终确认与历史身份、知识／题目／实验导入、chapter-plan 转为课程单元、综合题展示与分步自评／教师评阅入口、实验编辑器框架及草稿逻辑、判题适配、学生路径和画像验收。综合题自评首先作为学习进度；没有可靠评分证据时不自动提高掌握度。

本轮准备不修改题库数据库、不自动发布课程、不新建假题型接口。现有题目练习、算法模拟、编程实验三个独立入口继续保留，学习单元引用同一份资源。
