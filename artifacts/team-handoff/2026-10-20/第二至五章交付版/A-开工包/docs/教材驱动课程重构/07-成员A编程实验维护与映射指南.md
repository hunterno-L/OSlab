# 成员 A：已有编程实验维护与新映射指南

更新：2026-10-20。可直接交给 A。与 [题目工作指南](03-成员A题目整理与导入指南.md)、[第二至五章任务](19-第二至五章交付任务.md) 配套，课程和数据库设计由 L 维护。

实验按第二至五章的主归属独立交付：`A-第二章-实验维护-001` 等，与同章题目包分开。只交本章实际修订，不随每章重交全部盘点。第一章和原实验 ID／历史保留。当前重点是补齐编程栏起始框架、参考实现与真实用例，不只重交缺项清单。

## 1. 你的交付职责

除了补充题目，A 负责已有编程实验的持续维护，并建立两组关联：

| 关联 | 回答的问题 | 应填写的内容 |
| --- | --- | --- |
| 实验 → 新知识节点 | 这个实验真正验证什么能力 | nodeCode、PRIMARY／SECONDARY、权重和理由 |
| 实验 → 学习单元 | 学生学到哪里适合做这个实验 | unitCode、必需／可选、完成条件、安排理由 |

维护包括题面、实验目标、输入输出、样例、代码框架、参考实现、用例和现有标签。你把修订和映射整理为资源包提交 L；正式保存、导入、学生入口核对和判题证据验收由 L 执行。

L提供现有实验导出、正式节点及单元代码、数据库与映射工具、可用判题环境，并确认课程编排与发布。J 协助补充和核对缺少的知识实体。A 不需要设计表结构、搭建代码沙箱或自己写 Cypher。

## 2. 开始前拿到的资料

1. 现有实验清单：原 questionId、名称、题面、标签、旧章节、原始代码、参考答案、判题配置与用例；不要用学生接口导出后误以为管理字段为空。
2. 新节点词表：共享已有代码加 J 本章 knowledge.json，旧名称线索仍需按真实任务核对。
3. 学习单元清单：J 本章 chapter-plan.json。A 与 J 直接完善单元安排及缺失节点，最终发布由 L 确认。
4. A 开工包内的空白实验维护模板、单项填写样例与交接说明。

A 无需登录管理端。开工包提供项目 SQL 快照中的实验教学资料，L 在导入前负责与当前运行库核对差异。你先完成文件整理和映射，L 再处理导入与运行验证，三项状态分别记录。

当前快照包含 48 个有效实验。资料中部分实验缺少代码框架或参考解，inventory.json 已列待核对项；这些是 A 要维护的任务，不是空白模板或提取遗漏。历史快照中的程序未运行验收，不把“有代码”当作“可判题通过”。

## 3. 第一步：逐项盘点，保留原 ID

以已有 questionId 为主键清点，每个有效实验都要有记录。重复、缺代码、缺用例、题面不一致等问题写进维护清单，不为适配新课程重建另一份同名实验。

稳定资源代码建议采用 `exp.legacy.<questionId>`，或L已经分配的语义代码；后续改名仍沿用。导出 JSON 中 questionId 使用字符串，避免浏览器大整数精度损失。

先把实验分为：可直接使用、需内容修订、需判题条件修订、需运行环境处理、待确认适用章节。分类只帮助安排工作，不自动删除、停用或发布原实验。

## 4. 第二步：维护实验内容与用例

每项至少核对：

- 目标和题面要求是否一致，学生到底需要补什么函数／输出什么结果。
- 输入格式、输出格式、数据范围、单位和样例是否明确且互相匹配。
- 原始代码／代码框架是否保留必要上下文，参考实现是否完成题目要求。
- 样例输出是否可由规则和参考解独立复算；边界情况是否覆盖。
- 判题配置是否适合实际任务，所选语言与运行方式是否被现有环境支持。

现有系统的代码题以输入、运行、输出校验为主。如果某个历史实验依赖完整教学内核、启动镜像或指定硬件，需要把依赖和复现方法交给L适配，不能把普通终端程序通过当作内核实验已经通过。

优先修订题面、样例与用例中的确定错误，写进资源包中的 contentChanges 及配套文件。需要改变既有输入输出契约或执行方式时，把修改前后差异写清楚交 L 确认；历史提交及原 ID 继续保留。

在可用测试环境下，至少验证参考解通过、一个典型错误解失败、一个边界用例的输出。环境不可用时标明“文件已核对，尚未运行”，把环境问题交L处理，不猜测运行结果。

### 4.1 编程栏空白：必须交实际框架

先核对快照中的 originalCode，确认实验原有语言、接口和任务。需要补框架时提交 UTF-8 源文件，并在 contentChanges 写 `{field:"originalCode",file:"experiment-files/原ID/starter.c",reason:"补齐学生初始代码"}`。框架应有必要的头文件、数据结构、函数声明、输入输出或调用入口，以及清楚的 TODO；完整参考实现另交 reference.c，对应字段 answer。

当前 originalCode 是单个源码字符串，不支持 `{c:...,java:...}` 多语言字典；优先维护原有一种语言，语言、标准和启动命令写运行说明。确需多语言时可另附其他文件供后续接入，不把 JSON 字典当源码写入编辑器。框架本身应可编译或在原教学工程中可构建；学生未完成 TODO 时不能直接通过全部有效用例。

对完整教学内核代码保留真实上下文和任务，附需要的工程文件／头文件、替换位置、构建启动步骤及预期行为。缺项目来源时明确需要什么，不拿空函数、固定打印或无关算法替代原任务。

### 4.2 交付可复用的本地验证材料

把题面、starter、reference、judge-cases、必要 judge-config、典型错误实现和运行说明放 `experiment-files/原ID/`。参考解运行全部用例；至少一条用例能抓住对应误区，至少一条边界有独立预期。记录具体命令、工具链、输出和失败用例。已有本地编译器即可验证的任务由 A 完成，不统一留给 L 重跑推导。

平台应用后仍空白可能是浏览器 localStorage 的空草稿覆盖 originalCode；这项由 L 检查“无历史草稿”与“保留学生草稿”两种情况。A 无需修改前端工程。

## 5. 第三步：建立实验 → 节点映射

根据真实任务和判题能验证的内容选节点，不直接复制旧标签或整章所有节点。

示例：若任务要求实现 LRU 的命中更新及换出决策，主要映射为 `os.memory.lru`；只有任务同时检验缺页与换出计数时，才考虑把 `os.memory.page_replacement` 作为次要节点。题面提到页表或虚拟地址，不代表本实验真的能检测它们的理解。

默认主节点权重 1.0，确实能观测到的次节点可为 0.3。这是模型观测影响强度，不是评分占比，不要求相加为 1。不能仅为了让个人图谱更快变绿扩大关联范围。

缺少节点时，给 J 和L提交：候选名称、定义、对应教材范围、实验中可观察的行为、与已有节点的区别。J 补充实体与来源，L确认代码后你再建立正式关联。实现函数和教材概念可以分别建节点，再用 IMPLEMENTS 等语义关系连接。

## 6. 第四步：建立实验 → 单元映射

先读单元目标，确认实验所需知识何时已经学过。可安排为当前单元实践、多个单元后的综合实践，或可选拓展；一个实验可以服务多个单元，不复制实验正文和用例。

每个实际活动映射填写 unitCode、required、completionRule 和安排理由。`SUBMIT` 表示真实提交后活动完成，达标情况另看判题；`PASS` 表示只有后端判定通过才完成。是否必需与是否必须通过是两个不同设置。

第一章以概念学习为主。只有任务确实验证系统调用、中断、引导等本章主题且运行条件已具备时才纳入。与第一章只是背景相关的复杂内核实验，保留为后续章节实践；无需为每个第一章单元凑一个实验。

没有对应学习单元时，填写候选教材位置和理由，交L补充单元后再绑定。实验仍从独立入口使用，不因未安排课程活动而失效。

## 7. 交接文件格式

维护格式 `oslab-experiment-maintenance/1.0` 已有系统预览、保存草稿及审核 APPLY 支持，接口见 11 文档；它不是测评题导入格式。A 仍只交文件，由 L 上传与应用。

包字段：`schemaVersion: "oslab-experiment-maintenance/1.0"`、batchCode、contributor、experiments。

| 每个实验的字段 | 内容 |
| --- | --- |
| questionId | 必填，原实验 ID，JSON 中用字符串 |
| resourceCode | 必填，稳定资源代码 |
| title / sectionCode | 名称与主要教材目录，旧章节保留在交接记录 |
| contentChanges | 需要修订的题面、代码框架、参考解或用例；可附单独文件 |
| nodeMappings | nodeCode、role、weight、reason |
| unitMappings | unitCode、required、completionRule、reason |
| verification | 文件核对结果、运行结果、参考解及错误解案例、当前未解决项 |
| nodeProposals / unitProposals | 缺少正式编号时的结构建议，不冒充已存在映射 |

contentChanges 每项必须是 `{field,file,reason}`，field 仅可为 content／originalCode／answer／judgeCase／judgeConfig／tags，file 位于本包 experiment-files/ 下。没有内联 text／value 或 initialCode 字段。judgeCase 文件是非空的 `[{input:"...",output:"..."}]`；judgeConfig 至少有正数 timeLimit／memoryLimit；tags 是字符串数组。单个修订附件不超过 4 MiB，总量不超过 16 MiB，超出由 L 分次上传，章节仍一次交完整资源。

可复制的单项形状如下；使用时必须替换原 ID 及实际代码，删除不成立的候选关联。

```json
{
  "questionId": "替换为原实验ID",
  "resourceCode": "exp.legacy.原实验ID",
  "title": "原实验正式名称",
  "sectionCode": "sec.memory.page-replacement",
  "contentChanges": [],
  "nodeMappings": [
    {"nodeCode":"os.memory.lru","role":"PRIMARY","weight":1.0,"reason":"实际测试命中更新与换出决策"}
  ],
  "unitMappings": [
    {"unitCode":"unit.memory.lru","required":false,"completionRule":"PASS","reason":"学完规则后进行可选编程实践"}
  ],
  "verification": {"fileReview":"待核对","runtime":"尚未运行","cases":[],"openItems":[]},
  "nodeProposals": [],
  "unitProposals": []
}
```

示例 LRU 仅说明文件形状，不表示现有库中已经有该实验。具体绑定必须来自实际实验导出。

## 8. 提交资源包与 L 的系统核对

A 使用 experiment-work/ch02 等模板，提交 experiment-maintenance.json、experiment-files/、所需 assets/、交接说明和自审记录，压缩为 `A-第二章-实验维护-001` 等。L 先预览／保存修订草稿，审核 APPLY 更新原实验及正式映射，再在线验证与发布活动。无本章适用实验时说明即可，不交空包冒充修复。

以下四项由 L 在线核对，A 在交接说明里提供预期结果与验证案例：

1. 在独立编程实验入口能找到并提交原实验。
2. 从相关新节点能看到实验，实验详情能看到所考查知识。
3. 从学习单元能进入同一个实验，提交或通过后回到原活动位置。
4. 判题事件归入正式映射节点，个人实践证据与导师／教师统计使用同一套关联。

不能仅核对页面标签。正式映射使用 experiment_node，旧 tags 作展示及迁移线索；由 L 验证判题后的证据归属，A 提供准确映射与测试行为依据。

## 9. 每批交付清单

交付前按 [A 审查流程](16-A交付前审查流程.md) 的实验路径核对本批任务、实际修订、映射及验证。自审记录区分仅盘点、文件已修订和实际运行结果，不把实验代码存在或文件检查通过作为可判题证明。

- 已盘点实验、已修订实验、待处理实验的数量和原 ID 清单。
- 实验维护文件、样例／用例／参考实现及运行记录。
- 已确认的实验—节点与实验—单元映射。
- 需要 J 补充的节点、需要L补充的单元或执行方式。
- 文件整理结果、已有本地运行记录，以及需要 L 验证的入口和判题案例；不要求提交导入报告。

当前从第二章顺序维护到第五章：按本章清单实际补框架、参考解、用例和映射。跨章重复实验只维护一次，后续引用原 ID。资料快照与当前运行库由 L 接收时对比，A 不直接修改系统数据。
