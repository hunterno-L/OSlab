# J：整章知识包交付前审查流程

更新：2026-10-20。给 J 或负责复核 J 资源的 agent 使用。第二至五章按 [连续交付任务](19-第二至五章交付任务.md) 执行；第一章保留已有成果，每章交付／返修执行一次本流程。

目标是把资源中的问题改完再交 L。审查对象是实际 JSON、全部正文、关系和图片，交接说明只是核对依据之一。最终输出修订后的整章包和简短的 `自审记录.md`，不是只写一份“全部通过”的报告。

## 1. 准备输入并确定本次范围

先准备：本次 knowledge.json、assets/、交接说明、自己的教材、开工包 shared/ 词表，以及已收到的退修意见。

阅读 [J 工作指南](02-成员J教材切割与知识节点指南.md)、[协作数据规范](05-协作数据规范.md)、[第二至五章任务](19-第二至五章交付任务.md)。确定本次实际章范围，同时审查 chapter-plan.json。

实际执行：

1. 打开本次准备交付的文件，记录包名、版本、batchCode、教材版本和实际文件路径。
2. 从 JSON 计算节点、教学块、关系、图片数量，不能照抄交接说明的数字。
3. 逐条读取上一轮退修意见，标出需要修改的实际对象代码；本轮结束时逐条回查。
4. 确认本章包含全部适用正文、例题、图表和疑难点；不把前章空模板或样例计作本章已完成素材。

本步结果：确定唯一的审查版本，形成实际数量和问题清单。文件夹名字不完全一致等命名问题自行规范，不为此中断内容审查。

## 2. 先做文件与协议检查

在开工包根目录运行：

```powershell
node tools/check-member-package.mjs . --work-dir work/ch02
```

后续章替换 ch03／ch04／ch05。如果收到的是独立资源目录，可将 --work-dir 指向该实际目录（支持绝对路径），不必修改原件或重复复制。默认不传参数才检查旧 work/。正式自审不用 `--allow-empty`；该参数只用于检查空白模板。

同时核对机器检查未覆盖完整的字段：

| 对象 | 必须核对的规则 |
| --- | --- |
| 包 | schemaVersion=oslab-authoring/1.0，packageType=KNOWLEDGE，contributor=J；章代码、batchCode 与本章一致 |
| 节点 | nodeCode 唯一，名称与简介非空；nodeType 为 CONCEPT／ALGORITHM／MECHANISM／IMPLEMENTATION；layer 为 CORE／IMPLEMENTATION；aliases 为字符串数组 |
| 教学块 | chunkCode 唯一，chunkType 为 DEFINITION／EXPLANATION／ALGORITHM／WORKED_EXAMPLE／FIGURE／SUMMARY；nodeCodes 引用有效；正文和标题完整 |
| 出处 | 教材来源、目录、定位、印刷页范围正确；pageStatus 使用 VISIBLE／INFERRED／NOT_VISIBLE；正文 sourceQuestionNumber 为 null |
| 附件 | JSON 记录、Markdown 路径、实际文件一致，使用相对路径，没有电脑绝对路径或缺失文件 |

格式错误直接修正。新增或拆合节点保留真实候选说明，不为让检查器通过而换成不相干的已知节点。包内声明新节点能通过文件检查，不等于 L 已批准正式词表。

本步结果：记录实际命令、检查对象、退出结果和报错。文件检查通过之后，继续完成后续内容审查；它不检查知识正确性，也不能替代前置环和孤立节点审查。

## 3. 对照教材检查整章覆盖

打开教材，从章首顺序核对到章末。按正文小标题、图表、完整例子和疑难点列覆盖表，再逐项对应实际 chunkCode。

| 教材位置 | 实际印刷页码 | 对应 chunkCode／nodeCode | 图表或例子 | 结论或缺项 |
| --- | --- | --- | --- | --- |
| 实际标题 | 实际页码 | 实际代码 | 实际图号／无 | 已覆盖／具体问题 |

检查方法：

- 有标题不算有内容，必须打开对应教学块阅读。
- 习题精选、答案解析交 A，不要求 J 录成正文；教材正文中的完整例子仍要保留。
- 小结和章末疑难点关联已有知识，不机械新建同名概念。
- PDF 页序与印刷页码分开记。先用章首、章中、章末的实际页面确认对应关系，不直接套用其他文件的页码偏移。
- 不按节点数或教学块数凑工作量。一个机制的条件、步骤或图解缺失，即使已有很多短块仍属于缺项。

本步结果：整章覆盖表，明确缺哪些内容、哪些部分本来就不归 J。本章若仍缺关键正文，先补齐再标记整章内容自审通过。

## 4. 逐节点、逐块核对内容

全部阅读，不仅抽查开头几块。每个节点和教学块按以下顺序审查：

1. **对照教材**：定义、条件、否定词、分类、步骤、图表结论是否保持原意。ADAPTED 可以改写和概括，但不能省掉决定结论的条件。
2. **检查语义完整**：例子有输入、前提、过程和结论；机制解释能回答“为什么”或“怎样发生”；不把一个结论从必要上下文中单独摘出。
3. **检查节点关联**：内容确实解释了 nodeCodes 中的对象；同义概念复用代码，不能只因提到术语就关联所有节点。
4. **检查同章一致性**：同一术语在定义、正文、复习和关系中的含义一致；宽泛与狭义用法有清楚区分。
5. **按学生视角读一遍**：删除“本批如何建模”“后续复用某 nodeCode”“等待导入”等工程说明；改成自然的知识解释和章节指引。

第一章重点复核这些易混组：并发／并行、共享／同时占用、分时／实时、用户态／内核态、访管指令／特权指令、异常／外中断、子程序调用／系统调用、宏内核／微内核／外核、一般虚拟性／机器虚拟化。

技术限定保留在有助理解的位置，例如传统 BIOS/MBR 路径、教材模式位示意；与学习无关的免责声明、产品价格说明和资源整理过程移出正文。

教材表述之间有冲突时，回查具体页面和上下文，写明实际依据及建议措辞，不靠外部笔记或模型记忆宣布教材有错。明确的错字和解释矛盾自行修正；真正无法确定的语义问题集中交 L 决定。

本步结果：错误必须落到实际 nodeCode／chunkCode 并修改正文；记录少量关键修订及待确认事项，不需要把所有正确正文重抄一遍。

## 5. 单独审查每一条关系

逐条读出“哪个知识、以什么关系、指向哪个知识”，再对照 reason 和教材依据。

| relationType | 检查方法 |
| --- | --- |
| REQUIRES | 后学 → 前置；问“理解前者是否确实先需要后者”，不能拿教材出现顺序当证明 |
| CONTAINS | 父类／整体 → 子项；确认确有分类或组成关系 |
| BASED_ON | 算法／机制 → 依据；reason 说明它怎样利用该原理 |
| IMPLEMENTS | 实现 → 概念／算法；函数名不能直接代替完整概念 |
| CONTRASTS_WITH | 两端按代码字典序保存；比较维度成立，解释中的对象顺序明确 |
| RELATED_TO | 两端按代码字典序保存；写清具体联系，不只写“相关” |

完成三项整体检查：

1. 统计重复边、自指、未知端点，并检查 REQUIRES 是否有环。当前轻量文件检查器不会替你完成全部这些检查。
2. 列出孤立节点和主要断开的知识群，核对“操作系统、功能、接口、内核”等章内主干是否有合理联系。确有正文依据就补关系；无需强行连通所有节点。
3. 交叉核对 reason 与两端定义。尤其检查“前者／后者／分别”有没有因字典序保存而写反，优先直接写知识名称。

第一章反例：端点为“异常、狭义中断”时，不能把 reason 写成“分别来自当前指令外部与内部”；应明确写异常由指令执行引发，狭义中断来自当前指令之外。

本步结果：所有实际修改进入 relations；保留关系统计、前置环检查结果、孤立节点的处理说明。候选关系仍由 L 最终确认，不声称已写入线上图谱。

## 6. 打开每张图并顺读章节

实际打开所有图片，核对图号、图题、标签、箭头、表格行列、裁切边缘和可读性；存在文件不代表图片内容正确。图片、正文解读、sourceRef 必须指向同一张图及对应页。

随后依教材顺序读完整章的教学块，确认术语第一次出现时有解释，块之间不会因切割丢失指代，复习能回指前文。J 检查的是内容可读性，不需要做浏览器界面验收，也不需要代替 L 编排单元活动。

本步结果：图片总数及实际打开数量、需更换图片、内容衔接修订。不能把未打开的图片计为已视觉复核。

### 6.1 新增：审查学习单元草案并与 A 对齐

检查 chapter-plan 的目录新增项、单元目标、先修、阅读顺序和演示建议。readingChunkCodes 覆盖本章教学块，引用无误且顺序能连续理解；先修单元无环。不要把整章挤成一个长单元，也不把每段机械设为独立单元。

把本章节点与单元草案直接交 A 核对题目、综合题和实验关联；缺失的真实概念由 J 根据教材补上。记录已处理的 J/A 映射差异与仍需 L 确定的少量条目。L 不再负责替成员从原书重排全部阅读块。

## 7. 修改后回查，不只更新报告

先把已确定的问题改进 JSON、正文和图片，再执行：

1. 针对改动回查关联对象。例如改一个定义，要回查关联正文、复习块及关系；改图片路径，要回查 Markdown 和附件对象。
2. 重跑文件检查；涉及关系改动时重新检查重复、端点和前置环。
3. 从修订后的 JSON 重新计算数量，更新交接说明和给 A 的节点代码清单。
4. 对上一轮每条退修意见记录“改了什么、改在哪里、怎样复核”，未改的写实际原因，不能一概标“已处置”。

本步结果：实际包与自审记录一致。已明确错误仍未修正时，不给“内容自审通过”的结论。

## 8. 写自审记录并检查最终压缩包

将以下短记录保存为 `自审记录.md`，随整章包提交。也可以放在交接说明的独立“自审记录”一节，不必重复保存两份。

```markdown
# J 本章知识包自审记录

日期、包名、版本、batchCode：
审查者：
实际审查文件与教材版本：
实际范围：全部节点__、教学块__、关系__、图片__、单元建议__；未检查__。

## 实际结果

- 文件检查：实际命令、结果，或未运行及原因。
- 整章覆盖：范围及覆盖表位置，未覆盖内容。
- 教材对照：实际核对的印刷页和对象范围。
- 关系：重复／自指／未知端点／前置环结果，孤立节点处理。
- 图片：总数__，实际打开__，问题及处理。
- 单元：阅读块覆盖、目标、顺序与先修核对；J/A 编号及题目／实验关联对齐结果。

## 已修改

| 对象代码／文件 | 实际问题 | 实际修改 | 回查依据／结果 |
| --- | --- | --- | --- |

## 留给 L 的具体决定

仅列需要确认的新增／拆合编号、关系或教材争议，给出建议；没有则写无。

结论：内容自审通过／内容自审通过且有上述结构候选／尚未通过。
若尚未通过，写清缺项，不把未核对范围计为通过。
```

压缩后再打开最终压缩包，确认包含最新 knowledge.json、实际图片、交接说明和自审记录，未装入旧版文件、空模板或其他章节素材。正式交付仍是整章，修订不拆成逐节交付。

## 可直接交给审查 agent 的任务

> 请完整读取本流程、19 文档、最新协作规范和本章资源。审查本章全部节点、教学块、关系、图片及 chapter-plan，对照实际教材，完成阅读顺序和单元覆盖检查，并与 A 对齐本章节点／单元。确定问题直接改文件后复查，沿用稳定代码。交修订后的完整章包、自审记录和少量需要 L 决定的具体事项；不代替 L 导入或发布。
