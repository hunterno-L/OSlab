# OSLab 知识图谱智能学习闭环实施计划

> **给执行 agent：** 本文是执行依据。开始编码前先读完“现状与重构规则”和当前任务；不要把已有原型代码当成必须保留的实现。每个任务完成后先运行本任务的验证，再交给主 agent 合并。不要自行部署、推送或修改生产数据。

**目标：** 把 OSLab 从“知识图谱 + 实验题库”升级为一条可现场演示、可真实使用的学习闭环：普通题和实验提交产生学习证据，系统解释错误并更新个人知识图谱，随后推荐补救练习、交互模拟和实验验证。

**架构：** 保留现有 Vue 3 + Spring Boot + MySQL/Neo4j + 在线判题底座。普通题单独建模，不修改旧编程实验题表；MySQL 保存题目、作答、学习事件和学生节点掌握状态，Neo4j 继续保存知识节点及关系。前端采用一个通用的知识节点工作台，不为每个节点开发一套静态讲义页面。

**技术栈：** Vue 3、TypeScript、Arco Design、ECharts、Monaco Editor、Axios；Spring Boot 2.7、MyBatis-Plus、Java 17 运行时、MySQL、Neo4j；现有异步代码沙箱和判题链路继续复用。

## 全局约束

- 视觉基准固定为 design/frontend-concepts/2026-09-28/opendesign-knowledge-workspace.png。它是布局和信息层级参考，不是需要照抄的静态页面。
- 保留 OSLab 原有的顶部导航、课程侧栏、蓝色品牌强调色和三栏工作台结构；使用暖白/浅灰画布、1px 边框、4–12px 小圆角、少量阴影和紧凑信息层级。
- 禁止深色霓虹图谱、紫色渐变、玻璃拟态、过多胶囊标签、悬浮卡片堆叠、巨型 hero、虚假的 AI 对话占位和无数据的“智能推荐”。
- 普通题与编程实验分开存储。现有 question 表、旧题目 VO、旧判题请求和提交状态不得因为普通题功能而改字段或改含义。
- 题目标准答案只存在服务端；学生题目接口和普通题列表 VO 永不返回 answer、可接受答案数组或隐藏审核字段。
- 学习状态必须来自 learning_event。不允许前端写死“已掌握”、直接把答题次数当掌握度，或用随机数制造热力图。
- Neo4j 节点的业务键统一使用 EntityNode.name / nodeName。个人掌握状态、普通题映射和事件不得使用 Neo4j 内部自增 id。
- 不做每个节点一张静态讲义。节点内容由图谱描述、前置/后续关系、普通题、实验题、学习事件和少量结构化素材动态组合。
- 不引入消息队列、向量数据库、Python 训练服务或新的前端框架。GraphRAG 先用 Neo4j 一跳关系 + MySQL 题目/事件检索 + 现有 AI SDK。
- 本文不规定日历排期。执行顺序以任务依赖和验收门槛为准。

## 2. 统一演示主线与完成定义

用一个学生账号和一个教师/管理员账号跑通以下主线，所有功能都围绕这条路径组织：

~~~text
教师发布“LRU 页面置换”普通题
  -> 学生从知识图谱进入节点工作台
  -> 学生答错判断/单选/多选/填空题
  -> 服务端记录 attempt 和 event，更新 LRU 与前置节点状态
  -> 图谱节点呈现“待巩固”，右侧显示最近错误证据和原因
  -> 学生完成页面置换模拟器预测题
  -> 学生进入现有 LRU 编程实验并提交代码
  -> 判题终态写入学习事件，节点的实践应用分数改变
  -> 推荐下一道变式题或前置知识，教师看板能看到班级薄弱点
~~~

P0 的完成定义：

1. 四种普通题都能从章节列表和知识节点进入，服务端即时判分。
2. 答题前看不到标准答案，答题后可看到解析、错因和关联节点。
3. 一次普通题作答和一次编程实验终态都能留下可追溯事件。
4. 个人图谱节点颜色、状态和右侧证据随真实作答变化。
5. 至少一个页面置换模拟器能逐步展示 FIFO/LRU 的状态，并让预测结果进入学习事件。
6. AI 不可用时，普通题判分、图谱更新、推荐和模拟器仍可用。
7. 现场演示不出现假按钮、空白详情、前端伪造分数或只返回“请求成功”的操作。

### 3.2 题型判分

判分器保持纯函数，建议接口如下：

~~~java
public final class LearningQuestionGrader {
    public static boolean grade(String type, String answerJson, Object submitted);
    public static String normalize(String input);
}
~~~

规则固定为：

- JUDGE：服务端答案为 true/false，提交值 trim + 小写后比较。
- SINGLE：提交一个选项 key，大小写按选项 key 规则处理，不能提交不存在的 key。
- MULTIPLE：提交 key 数组，集合完全相等；顺序不影响结果，缺一个或多一个都算错。
- FILL_BLANK：服务端保存可接受答案数组；提交 trim、合并连续空白、按课程规则统一大小写后匹配。

作答响应可以返回：

~~~json
{
  "correct": false,
  "attemptId": 1001,
  "isFirst": true,
  "analysis": "命中后仍需更新最近访问顺序。",
  "misconception": "把命中当成不需要更新顺序。",
  "masteryChanges": [
    {"nodeName":"LRU 页面置换算法","before":0.54,"after":0.38,"status":"YELLOW","reason":"首次判断题答错"}
  ]
}
~~~

响应中绝不出现 answer 或答案数组。

### 3.3 掌握度模型

使用可解释的 BKT，不接入训练模型。把计算放在一个无状态纯类中，参数集中定义：

~~~java
double update(double pKnown, boolean correct,
              double pLearn, double pGuess, double pSlip);
~~~

建议默认参数 pInit=0.10、pLearn=0.10、pGuess=0.20、pSlip=0.10。一次独立观测的顺序是：先按对错求后验，再应用学习转移；重复刷同一题不增加 observationCount，但仍保留 attempt/event 记录。

- ATTEMPT 更新 conceptScore，因为普通题主要验证概念理解。
- JUDGE 和 SIMULATION 更新 practiceScore，因为它们验证算法应用。
- pKnown 作为综合状态：普通题和实践事件按映射权重更新；推荐和状态解释同时读取两个分项。
- 状态阈值固定：无证据为 GRAY；pKnown < 0.35 为 RED；0.35 <= pKnown < 0.70 为 YELLOW；pKnown >= 0.70 且至少有两类证据为 GREEN。
- confidence 反映证据量和来源种类，不能等同于掌握度。UI 必须同时显示分数和可信度/证据数量。

### 3.4 学习事件与幂等

所有状态变化通过事件服务完成，接口至少包括：

~~~java
List<MasteryChangeVO> recordAttemptEvents(
    Long userId, LearningQuestion question,
    Long attemptId, boolean correct, boolean first);

void recordJudgeEvents(long questionSubmitId,
                       int terminalStatus, String judgeMessage);

Long recordSimulationEvent(Long userId, String nodeName,
                           String simulationKey, boolean correct,
                           String evidence);
~~~

幂等键固定为：

~~~text
attempt:{attemptId}:{nodeName}
judge:{questionSubmitId}:{nodeName}
sim:{userId}:{simulationKey}:{nodeName}
~~~

唯一键冲突时返回已经存在的事件，不重复计算 BKT。系统错误不作为学生答错证据；普通题提交本身的结果必须可回放。

## 8. Phase 3：事件账本、BKT 与实验判题接入

### 文件

- 测试：后端代码/osLab-backend/src/test/java/com/yupi/springbootinit/bkt/BktModelTest.java、learning/ 下的事件测试

### 操作

1. 先为 BKT 写纯函数测试：答对后上升、答错后下降、重复输入结果稳定、边界值在 0 到 1 之间。
2. 事件服务在一个事务内完成：校验节点 -> 生成幂等键 -> 读取旧 mastery -> 计算分项和综合状态 -> 插入事件 -> upsert mastery。事件插入时直接写 masteryBefore/After，不要插入后再偷偷修改历史事件。
3. recordAttemptEvents 对题目映射的每个节点产生事件；重复 attempt 只保留证据，不增加独立观测。
4. 在 JudgeServiceImpl 的成功/失败终态之后调用 recordJudgeEvents。只把 Accepted、Wrong Answer、Runtime Error、Time Limit 等学生可见终态映射为 PASS/FAIL；沙箱系统错误记录 SYSTEM_ERROR，不降低掌握度。
5. 个人图谱接口读取旧 Neo4j 图谱后批量合并 mastery。没有学习记录的节点返回 GRAY 和空证据，不生成假分数。
6. 推荐排序固定为：前置节点为红色 > 最近连续失败 > 有未完成普通题 > 有可用模拟器/实验；每条推荐必须带 reason。

### 验收

- BKT 单元测试通过，旧 QuestionSubmit 状态和判题响应不变。
- 同一个 idempotencyKey 重试不会多出事件或二次更新 mastery。
- 一次普通题答错能看到 before/after 和证据；一次实验 Accepted 能提高 practice 分项。
- 系统错误不会把学生节点标红。
- GET /learning/mastery/graph 返回每个节点的 status、pKnown、confidence、conceptScore、practiceScore、recentReason。

### 不要做

- 不要在 Controller 里重新计算 BKT。
- 不要在判题轮询中重复写事件；只接终态。
- 不要把所有事件都写成“普通题答错”，来源必须可区分。

每一步结果必须包括：访问页、命中/缺页、当前帧、被淘汰页、算法解释。预测模式让学生在下一步提交“是否缺页”和“淘汰页”，服务端用同一个算法真值判分。

- 确认 Neo4j、MySQL、Redis 的部署配置仍来自 deploy/.env，不把本地密码写进源码或 SQL。
- 记录前后端构建、测试和手工主线结果；只把实际通过的项目写进完成说明。
